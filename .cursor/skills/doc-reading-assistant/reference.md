# 文档阅读助手：参考规范

本文件存放可选的细节策略，用于让“文档阅读助手”在面对长文档、英文文档、多链接与抓取受限页面时，依然能稳定输出高质量结果。

## 1. 何时使用本技能

当用户出现以下任一信号时，应该启用本技能的流程：

- 用户提供 **URL** 并要求“阅读/总结/翻译/概括/提炼要点”
- 用户提到“文档太长”“英文看不动”“帮我快速理解/翻译一下”
- 用户希望你基于文档回答具体问题（例如“这个 API 怎么用”“为什么这么设计”）

## 2. 输入约定（推荐引导）

若用户没有明确参数，可建议用户按如下格式补充（但不要强制）：

- URL：`https://...`
- 模式：总结 / 翻译
- 输出长度：短 / 中 / 长
- 关注点：概念 / 实现 / API / 迁移 / 踩坑
- 翻译风格（翻译模式）：直译 / 意译 / 双语

## 3. 抓取与阅读策略（含失败兜底）

### 3.1 首选：直接读取页面内容

- 对技术文档优先提取：标题层级、段落、列表、表格、代码块、警告提示（Note/Warning/Tip）。
- 忽略常见噪声：顶部导航、侧边栏目录重复、页脚版权声明、评论区、推荐阅读。

### 3.2 抓取失败/受限页面的兜底

若出现以下情况：需要登录、反爬限制、内容为空、只返回骨架 HTML、或无法访问：

- **替代来源**：尝试找到同一主题的官方镜像、GitHub README、发布公告、或静态渲染版本。
- **最小请求用户补充**：请用户粘贴“目录 + 关键小节”或截图（优先 1–3 个最相关段落）。
- **避免硬编**：不要在未读到关键段落时臆测细节；用“我从文档片段中能确认的是…”与“需要原文补充才能确认的是…”明确边界。

## 4. 长文档分段与输出节奏

### 4.1 先大后小

对较长文档，优先输出：

- 文档主题一句话
- 目录级大纲（按标题层级）
- 关键结论与重要警告

然后再进行逐节总结/翻译。

### 4.2 分段原则

- 以标题（H1/H2/H3）作为天然切分点。
- 表格与代码块保持整体，避免截断导致含义缺失。
- 若文档是“步骤型教程”，以步骤块切分（Step 1/2/3）。
- 若文档是“参考手册”，以 API/模块为切分单位。

## 5. 总结模式：质量标准

### 5.1 必须覆盖的内容

- **目的**：文档要解决什么问题
- **结论**：推荐做法/默认配置/最重要规则
- **边界**：适用条件与不适用场景
- **风险**：常见坑、兼容性、性能/安全注意事项

### 5.2 建议增加的价值

- 对“为什么这样设计”给出合理解释（以文档证据为主）
- 把隐含前置条件写出来（环境、版本、权限、依赖）
- 给出“最小可行行动项”（用户下一步怎么做）

## 6. 翻译模式：质量标准

### 6.1 术语一致性

- 建立“术语表”：英文 → 固定中文译名
- 同一概念避免多种译法混用
- 对容易误解的术语（如 consistency, isolation, fairness）可加译者注

### 6.2 保留信息结构

- 标题层级、列表编号、代码块、参数名、命令、文件路径 **保持原样**
- 单位、符号、版本号、API 名称不要“翻译变形”

### 6.3 风格选项

- **直译**：信息密度最高，适合工程实现
- **意译**：更顺畅，适合科普与阅读理解
- **双语对照**：适合学习术语与精准核对

## 7. 多链接对比输出

当用户给出多个链接：

- 先为每个链接给出一句话定位（主题/版本/视角）
- 再输出对比表（或列表）：一致点、差异点、冲突点
- 明确指出差异可能来自：版本差异、不同实现、不同语境/假设

## 8. 合规与版权注意

- 只引用必要的短片段用于定位与避免歧义，避免长段落逐字复制。
- 若用户明确需要“全文翻译”，也应优先建议“翻译关键章节/按需翻译”，并在输出中保持节制。

## 9. 新建 Markdown 文档的写作规范（本项目约束）

当本技能要求“新建一篇文档来记录”时，必须严格遵循本项目的统一写作规范：

👉 **[.cursor/skills/writing-style/SKILL.md](../writing-style/SKILL.md)**

关键要点速查：
- **Frontmatter**：必须包含 `title`, `aliases` (UUID v4), `date`, `tags`, `card`, `order` 等字段。
- **链接**：内部使用 `[[aliases|title]]`，外部使用 `[title](url)`。
- **排版**：中英文空格、空行、代码块语言标签、长代码折叠 (>10行)、Callout 类型等均以 `writing-style` 为准。

## 10. 善用原文资源（图片 / 表格 / 文件 / 示例）

为了最大化“可理解性”和“可复用性”，归档文档应尽量复用原文资源，但要做到“为理解服务”：

### 10.1 图片与图表（优先）

- **优先嵌入**：遇到架构图、状态机图、流程图、关键对比图时，优先把图片放入归档文档中，并在图片下方补一行说明“这张图在解释什么”。
- **本仓库推荐做法**：
  - 将图片保存到 `content/assets/`
  - 在文档中使用 Obsidian/Quartz 兼容的嵌入方式：`![[图片文件名.png]]`（或 `![[/assets/图片.png]]` 视现有习惯）
  - 若无法本地保存图片，则使用标准 Markdown 外链：`![caption](https://...)`
- **避免堆图**：只保留“能显著降低理解成本”的图；对装饰性或重复信息的图可省略。

### 10.2 表格与清单

- 对“参数表/对比表/状态位定义”这类高价值内容：
  - **优先转为 Markdown 表格**（便于检索与本地维护）
  - 或者摘录为“要点列表 + 解释”，并保留原文链接用于溯源

### 10.3 代码与配置示例

- **原样保留关键示例**：代码块、命令、配置项保持结构与语义不变（避免翻译导致不可运行）。
- **补充最少必要上下文**：说明适用版本、前置条件、常见错误与输出含义。
- **长代码折叠**：遵循 `writing-style` 的 code fold 约定，避免正文被大段代码淹没。

### 10.4 文件/附件/下载资源

- 若原文提供可下载文件（PDF、示例仓库、数据文件、白皮书等）：
  - **优先记录来源与用途**：在文档中写清“这个文件用于什么、怎么用、注意什么版本/权限”
  - **存放策略**：小文件可放入 `content/assets/` 并在文档中链接；大文件优先仅保留外链与关键节选
