# Guided Tech Writing (引导式技术写作)

## Description
规范技术博客和源码阅读文章的写作口吻，采用“专业且具有启发性的引导式教学”风格。当用户要求撰写、重写、导读源码或技术文章时，应遵循此技能中的写作规范。

## Context
在撰写技术解析、源码导读等文章时，传统的平铺直叙容易显得枯燥乏味，而过度口语化（如“幼教式”口吻）又会削弱技术文章的专业性和严谨性。本技能旨在寻找两者的平衡点：以专业严谨的技术术语为基础，通过抛出问题和启发式思考来引导读者阅读。

## 1. Tone & Voice (基调与口吻)
- **专业严谨 (Professional & Accurate)**：必须使用准确的计算机科学和编程术语。保持工程师之间的对话感：平等、理性、客观。
- **启发引导 (Heuristic & Guided)**：善用设问句推动行文逻辑。在讲解复杂逻辑或边界情况前，先抛出问题引导读者思考，解释其背后的设计哲学（Why），而非仅仅翻译代码（What）。
- **直接了当 (Direct)**：例如“使用连接池”，而不是“您可能需要考虑使用...”。
- **客观中立 (Objective)**：承认权衡与妥协（Trade-offs），例如“这增加了系统的复杂性”，而不是假装解决方案是完美的。使用具体数据（如“将 p99 延迟降低到 90ms”）代替模糊形容词（如“显著提升”）。
- **明确受众 (Audience)**：在文章开头明确设定受众门槛，例如“本文假设您熟悉 Docker 基础...”。

## 2. Anti-Patterns (常见反模式)
**必须严格避免以下表达：**
- ❌ **幼教化/过度拟人化**：绝对避免使用“小本本”、“抓壮丁”、“掀桌子”、“坑位”、“闲人免进”等轻浮词汇。
- ❌ **生硬做作的书面语**：如“剥开其语法糖，直击它在运行时的真实面貌”。尽量像资深工程师在进行技术分享一样自然流畅。
- ❌ **废话开场白**：“在当今快节奏的技术世界中...” (直接删掉，直奔主题)。
- ❌ **故作高深或理所当然**：“众所周知...” (既然大家都知道，你为什么还要写？)。
- ❌ **轻视难度**：“只需简单地执行 X...” (如果读者在看教程，说明这并不简单，禁用“简单地”、“只需”等词汇)。
- ❌ **缺乏 TL;DR**：没有在开头提供 2-3 句话的核心总结，导致读者失去耐心。
- ❌ **隐藏缺点**：没有“权衡与局限性”章节，让人感觉像是有偏见的营销软文。

## 3. Content Structure (内容结构)
根据不同的写作目的，采用以下标准结构，并保持**逻辑递进 (Logical Flow)**，将复杂原理拆解为清晰的步骤（带有明确的小标题和核心目标）：

- **教程/指南 (Tutorial / How-To)**
  - **目标**：提供可操作的步骤，读者可以跟着构建出具体成果。
  - **结构**：1. 我们要构建什么（附带截图/演示） -> 2. 前置条件 -> 3. 步骤 1：环境配置 -> 4. 步骤 2：核心实现 -> 5. 完整代码（提供链接） -> 6. 下一步/扩展阅读。
- **深度解析 (Deep Dive / Explainer)**
  - **目标**：深入解释某个概念、技术或架构决策。
  - **结构**：1. 什么是[概念]，为什么你需要关心？ -> 2. 它是如何工作的（简化的心智模型） -> 3. 它是如何工作的（详细的底层机制） -> 4. 真实世界的使用案例 -> 5. 权衡取舍（Trade-offs）以及何时**不**该使用它 -> 6. 扩展阅读。
- **架构设计 (Architecture / System Design)**
  - **目标**：解释系统是如何构建的，以及为什么做出这些决策。
  - **结构**：1. 我们需要解决的问题 -> 2. 约束条件与需求 -> 3. 曾考虑过的备选方案 -> 4. 最终选择的架构（必须附带架构图） -> 5. 我们接受的权衡与妥协 -> 6. 结果与经验教训。

## 4. Code & Examples (代码与示例规范)
- **聚焦核心，剥离噪音**：在展示源码时，适当省略与当前上下文无关的防御性代码或竞态检测代码（或一笔带过），将注意力集中在核心算法和主干流程上。
- **必须可运行**：损坏的代码示例会彻底破坏读者的信任。
- **提供完整上下文**：不要只提供缺乏上下文的代码片段。
- **展示执行结果**：在代码块之后展示预期的输出/结果，帮助读者验证理解。
- **包含错误处理**：真实世界的代码都有错误处理，示例代码也应包含。
- **锁定依赖版本**：注明“适用于 React 18.2”，而不是含糊的“适用于 React”，防止代码在未来失效。
- **使用有意义的命名**：使用 `calculateTotalRevenue`，绝对不要使用 `foo`、`bar`。

## 5. Examples (正反例对比)

### ❌ 反例 1：过于干瘪（像机器翻译）
> `mapassign` 函数不接收 value 参数。它遍历 bucket 查找 key，如果找到就返回地址。如果 bucket 满了，它会调用 `hashGrow` 扩容或者 `newoverflow` 分配新桶。

### ❌ 反例 2：过度口语化/幼教化
> 仔细看看这个函数，你发现什么不对劲了吗？它居然没有 value 参数！如果坑位满了怎么办？Go 可不会盲目扩容，如果只是局部拥挤，它会给这个 bucket 开个小灶，挂个新的溢出桶。

### ✅ 正例：专业且具启发性
> 观察这个函数的签名，你会发现一个有趣的细节：`mapassign` 并没有接收 value 作为参数。它的核心职责是寻址。
> 
> 那么，如果遍历完了所有的常规桶和溢出桶，都没有找到目标 key，且当前 bucket 已经满载，此时该如何处理？
> 面对满载的 bucket，Go 会依次进行两步判断：首先评估全局健康度（是否需要扩容）... 其次处理局部冲突（动态分配溢出桶）...
