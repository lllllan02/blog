# Guided Tech Writing (引导式技术写作)

## Description
规范技术博客和源码阅读文章的写作口吻，采用“专业且具有启发性的引导式教学”风格。当用户要求撰写、重写、导读源码或技术文章时，应遵循此技能中的写作规范。

## Context
在撰写技术解析、源码导读等文章时，传统的平铺直叙容易显得枯燥乏味，而过度口语化（如“幼教式”口吻）又会削弱技术文章的专业性和严谨性。本技能旨在寻找两者的平衡点：以专业严谨的技术术语为基础，通过抛出问题和启发式思考来引导读者阅读。

## Core Principles (核心原则)

1. **专业严谨 (Professional & Accurate)**
   - 必须使用准确的计算机科学和编程术语。
   - **绝对避免**过度拟人化、幼教化或过于轻浮的口语表达（例如：禁用“小本本”、“抓壮丁”、“掀桌子”、“坑位”、“闲人免进”等词汇）。
   - 保持工程师之间的对话感：平等、理性、客观。

2. **启发引导 (Heuristic & Guided)**
   - 善用设问句推动行文逻辑。在讲解复杂逻辑或边界情况前，先抛出问题引导读者思考。
   - 例如：“但是，如果当前 bucket 及其溢出桶已经全部满载，此时该如何处理？” -> 随后再给出源码的解答。
   - 引导读者关注代码签名、异常分支或反直觉的设计，并解释其背后的设计哲学（Why），而非仅仅翻译代码（What）。

3. **逻辑递进与结构化 (Logical Flow)**
   - 将冗长复杂的源码或技术原理解构为清晰的、有先后顺序的步骤（如：1. 前置检查 -> 2. 计算哈希 -> 3. 延迟初始化...）。
   - 每个步骤都应有明确的小标题，并在段落开头点明该步骤的核心目标。

4. **聚焦核心，剥离噪音 (Focus on the Core)**
   - 在展示源码时，适当省略与当前上下文无关的防御性代码或竞态检测代码（或一笔带过），将读者的注意力集中在核心算法和主干流程上。

## Examples (正反例对比)

### ❌ 反例 1：过于干瘪（像机器翻译）
> `mapassign` 函数不接收 value 参数。它遍历 bucket 查找 key，如果找到就返回地址。如果 bucket 满了，它会调用 `hashGrow` 扩容或者 `newoverflow` 分配新桶。

### ❌ 反例 2：过度口语化/幼教化
> 仔细看看这个函数，你发现什么不对劲了吗？它居然没有 value 参数！如果坑位满了怎么办？Go 可不会盲目扩容，如果只是局部拥挤，它会给这个 bucket 开个小灶，挂个新的溢出桶。

### ✅ 正例：专业且具启发性
> 观察这个函数的签名，你会发现一个有趣的细节：`mapassign` 并没有接收 value 作为参数。它的核心职责是寻址。
> 
> 那么，如果遍历完了所有的常规桶和溢出桶，都没有找到目标 key，且当前 bucket 已经满载，此时该如何处理？
> 面对满载的 bucket，Go 会依次进行两步判断：首先评估全局健康度（是否需要扩容）... 其次处理局部冲突（动态分配溢出桶）...
