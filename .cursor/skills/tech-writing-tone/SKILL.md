# ✍️ Tech Writing Tone & Structure (技术写作基调与结构)

**⚠️ 核心准则：本指南定义了当前项目所有技术文章（特别是 content/ 目录下）的内容基调与结构。在生成、撰写、修改或优化文档内容时，必须严格遵守以下规范。**

## 1. Tone & Voice (基调与口吻)
- **专业严谨 (Professional & Accurate)**：必须使用准确的计算机科学和编程术语。保持工程师之间的对话感：平等、理性、客观。
- **启发引导 (Heuristic & Guided)**：善用设问句推动行文逻辑。在讲解复杂逻辑或边界情况前，先抛出问题引导读者思考，解释其背后的设计哲学（Why），而非仅仅翻译代码（What）。
- **直接了当 (Direct)**：例如“使用连接池”，而不是“您可能需要考虑使用...”。
- **客观中立 (Objective)**：承认权衡与妥协（Trade-offs），例如“这增加了系统的复杂性”，而不是假装解决方案是完美的。使用具体数据代替模糊形容词。
- **连贯叙述优先**：多使用完整的自然段落进行连贯叙述。严格控制列表和 Callout（提示块）的滥用，避免内容过度碎片化或变成单纯的“要点堆砌”。

## 2. Anti-Patterns (常见反模式)
**必须严格避免以下表达：**
- ❌ **幼教化/过度拟人化**：绝对避免使用“小本本”、“抓壮丁”、“坑位”等轻浮词汇。
- ❌ **生硬做作的书面语**：如“剥开其语法糖，直击它在运行时的真实面貌”。尽量像资深工程师在进行技术分享一样自然流畅。
- ❌ **废话开场白**：“在当今快节奏的技术世界中...” (直接删掉，直奔主题)。
- ❌ **故作高深或理所当然**：“众所周知...” (既然大家都知道，你为什么还要写？)。
- ❌ **轻视难度**：“只需简单地执行 X...” (禁用“简单地”、“只需”等词汇)。
- ❌ **缺乏 TL;DR**：没有在开头提供核心总结，导致读者失去耐心。
- ❌ **隐藏缺点**：没有“权衡与局限性”章节，让人感觉像是有偏见的营销软文。

## 3. Content Structure (内容结构)
根据不同的写作目的，采用以下标准结构，并保持**逻辑递进 (Logical Flow)**：
- **教程/指南 (Tutorial / How-To)**：1. 目标 -> 2. 前置条件 -> 3. 步骤 1... -> 4. 完整代码 -> 5. 下一步。
- **深度解析 (Deep Dive / Explainer)**：1. 概念与动机 -> 2. 简化心智模型 -> 3. 底层机制 -> 4. 真实案例 -> 5. 权衡取舍 (Trade-offs)。
- **架构设计 (Architecture / System Design)**：1. 待解决问题 -> 2. 约束与需求 -> 3. 备选方案 -> 4. 最终架构 -> 5. 权衡与妥协 -> 6. 经验教训。

## 4. Code Examples (代码示例规范)
- **聚焦核心**：适当省略与当前上下文无关的防御性代码，将注意力集中在核心算法和主干流程上。过长的代码应进行折叠或仅摘录核心片段。
- **必须可运行**：损坏的代码示例会彻底破坏读者的信任。包含错误处理，展示执行结果。
- **锁定依赖版本**：注明“适用于 React 18.2”，防止代码在未来失效。
